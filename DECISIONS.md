# Decisions

*All phases complete — data/ETL, backend, frontend, Docker packaging, README, QA, a red/blue-team audit, and the corrections it produced (below). Trimmed to one page below.*

## What's built so far
A DuckDB warehouse (`etl/build_warehouse.py`) cleaning all 13 raw tables plus BazaarPulse scrape + freight API pull + inventory snapshots into documented fact/dim tables; a FastAPI backend serving read-only analytics over it (no route or query touches the raw operational tables — the raw schema is physically dropped after the warehouse build); a React/Vite dashboard (Overview, Service, Money, Cold Chain, Price Position, Ask Anything) consuming that API, including a region scope selector for regional managers; Docker Compose packaging five services (mock BazaarPulse site, mock partner API, one-shot ETL job, backend, frontend) with health-gated startup order; and a pytest suite (`backend/tests/`) covering SQL-guard security cases, validation regressions, and the 8 illustrative questions end-to-end against the real warehouse.

## Priority allocation
Fill Rate/OTIF 30%, Ask-anything 30%, Freight+Returns 25%, Cold Chain 10%, Price Position 5% — set explicitly, depth follows this order.

## Judgement calls

**Fill rate: eaches, not cases — locked, no toggle in the API.** The brief's own illustrative Q1 says "case fill rate," but Rakesh Menon's follow-up email explicitly overrides it: modern trade penalises Kestrel on units short, not cases short, and mixed-configuration SKUs make cases ambiguous. We apply eaches uniformly, including when literally answering Q1, and say so in the answer rather than silently switching units.

**OTIF: no in-full tolerance threshold.** Investigated rather than assumed: 0 of 511,516 order lines — across every order_status including DELIVERED — ever have delivered_eaches >= ordered_eaches; 99th percentile of order-level fulfilment is 94.8%. Every line carries a real shortfall by data design. A blended OTIF at the strict 100% bar is therefore ~0% almost everywhere. We report it that way — not tuned to an arbitrary tolerance to make it "look normal" — and expose on-time % and avg fulfilment % (continuous, not boolean) alongside it as the usable signal. Kestrel's own shrinkage-tolerance policy would be needed to define a real in-full threshold; that's a business decision we don't have.

**delay_minutes used as-is, not recomputed from timestamps.** Checked: delay_minutes disagrees with (actual_arrival − planned_arrival) computed from the parsed timestamp columns in 87% of deliveries, including sign. Used the documented field (data dictionary defines its sign convention directly) rather than substitute our own derivation that the data itself doesn't corroborate.

**Fiscal year: year-ending label.** FY runs April–March; labelled by the year it ends in (Indian convention), so Apr–Jun 2026 is **FY2027 Q1**, not FY2026 Q1. Verified across all quarters, not just one.

**Near-expiry: implemented, not cut.** `inventory_snapshots` was outside the initial warehouse build; a quick feasibility pass showed it was one clean fact table (weekly, expiry_date always populated, no format surprises) — added `fact_inventory_snapshot` and `GET /cold-chain/near-expiry`. Near-expiry is computed from `expiry_date − snapshot_date` directly, **not** from the source `ageing_bucket` column: checked, and that column is uncorrelated with actual days-to-expiry (all four buckets average ~100 days regardless of label) — it's carried through for reference but not trusted.

**Price position: conservative matching, not loosened.** BazaarPulse listings are matched to Kestrel SKUs by (brand, category, normalised pack size), with a product-name-overlap tiebreak. 614 of 1,137 listings match with confidence; the remaining 523 stay `ambiguous` and are excluded from every price-gap view rather than guessed. This rate was not inflated on review.

**OTIF now supports `group_by=outlet`, matching fill rate.** The brief asks for both metrics "by region, by warehouse, by route, by outlet"; fill rate always had all four, OTIF was missing outlet (an oversight caught in audit, not a deliberate cut — `fact_deliveries` already carried `outlet_id`, it just wasn't selected into the OTIF query). Added using the same `dim_outlet` config fill rate already uses; the strict, no-tolerance in-full definition is unchanged.

**Regional-manager view: a region filter, not a new auth system.** The brief: "Make it work for the regional managers too, they will want their own view." Implemented as a `region_code` scope — a selector in the top bar (default **All Regions**, backed by `GET /meta/regions`), threaded through Service, Money, Cold Chain, and Ask Anything as an optional query/body param. Deliberately not accounts, roles, or permissions: anyone can switch region, it only narrows what's shown, consistent with everything else in this build being a single-tenant ops tool. **Price Position is the one exception**, and it's surfaced in the UI rather than silently ignored: competitor listings are scraped by city (Mumbai/Delhi/Bengaluru/Chennai), which has no mapping to Kestrel's own 5 sales regions in this dataset, so the page shows an explicit callout instead of pretending to filter. Freight's region scope is applied via the delivering route's region (`dim_route.region_id`) since invoices don't carry an outlet/order key to scope through directly — same "filtered independently, not line-by-line reconciled" caveat that already applied to freight's period filter.

**Q5 (late routes) and Q8 (discontinued-SKU orders): reported as systemic, not per-entity blame.** All 140 routes exceed ">2hr late on >10% of deliveries" (avg delay ~132 min network-wide); all 721 production outlets (724 total, excluding the 3 known test/migration outlets, same rule as fill_rate/otif) have at least one post-discontinuation order line across 24 discontinued SKUs, continuing to the end of the dataset. Both are framed as process/network findings, with worst-offender rankings included for follow-up, not as "these specific entities are broken."

**Known-issue log spot-check.** KP-2301 (order header vs. line value mismatch) did not reproduce — gross ties to `sum(line_value_inr)` exactly; net differs only by discount/tax as expected. Not chased further.

**Data cleanup applied once, in the warehouse build:** city spelling (KP-2288), outlet dedup by GST/geo not name (KP-2211, ~6 outlets, not hundreds), test-outlet exclusion by name pattern (KP-2377, exactly 3), return-quantity sign correction (KP-2402, abs()), per-source timestamp parsing (3 order-creation formats, 2 telematics formats).

## Ask Anything: LLM NL-to-SQL, now implemented (supersedes the earlier "deferred" decision)
The 8 illustrative questions remain deterministic fast paths — keyword-matched, hand-written, tested, zero external dependencies, and they always take priority even when an LLM key is configured. Anything else is now answered for real: the question goes to Groq (`GROQ_API_KEY`, default model `llama-3.3-70b-versatile`) along with a compact, hand-written schema description (table/column names only, filtered through the privacy policy below — no live data, nothing from the raw operational tables, which don't even exist in the warehouse file the backend opens). Groq returns `{sql, answer_intro}` JSON; the SQL is **never trusted or executed directly** — it goes through the exact same `sql_guard.validate_readonly_sql()` that was hardened across the earlier audits (Section "SQL guard" below), so a mutation statement, a disallowed table, a comma-joined table list, or any of the other closed bypasses fails the same way regardless of whether the SQL came from a human or a model. Three distinct failure points (the Groq call itself, the guard, and query execution) each degrade to a clean `mode="llm_error"` response with no data — never a 500, never a silently wrong answer. The generated SQL is always shown alongside the answer, same as the two fast paths (`q5`, `q8`) that already showed their SQL — auditability was already a design principle here, not something added for the LLM path. Region scoping for free-form questions is a prompt instruction to the model, not a structural guarantee the way it is on the fixed dashboard endpoints; the UI says so when a region is selected. `ANTHROPIC_API_KEY`/`ANTHROPIC_MODEL` remain in config for compatibility with earlier docs but no code path calls them.

## Personal data protection (Ask Anything)
Personal data is protected through deterministic schema allowlisting, input redaction/blocking, SQL-level privacy validation, and result validation. The LLM never receives protected personal-data columns. This is rule-based (`backend/app/privacy.py`), not a second LLM asked to judge what's personal — every check is a static list or a regex, on purpose, so it's auditable and doesn't depend on a model's judgement.

What's actually personal in this dataset (found by inspecting the real raw schema and the live warehouse — not invented): `dim_outlet.contact_name`/`contact_phone`/`contact_email` (the outlet's contact person) and `gst_number` (a government-issued tax ID); `dim_salesperson.full_name`; `dim_warehouse.manager_name`; `dim_region.regional_manager` (this last one is legitimately shown in the region-selector UI via `GET /meta/regions`, a fixed, brief-driven feature unrelated to free-form querying — blocking it from the LLM path doesn't touch that endpoint). Everything else — `outlet_code`, `route_code`, `warehouse_code`, `sku_code`, `region_code`, and the rest of the operational identifiers the app runs on — is explicitly *not* personal data and stays fully available to free-form questions.

Four layers, all in `ask.py`'s request flow, before/after the existing SQL guard:
1. **Schema filtering** — the hand-written schema description sent to Groq excludes every blocked column by construction; an `assert` at import time fails the container's own startup if a blocked column name ever appears in it.
2. **Question-level blocking** — a fixed phrase list catches a request *for* a personal-data category ("show customer phone numbers") before Groq is ever called; a regex layer catches a PII-shaped *value* embedded in the question (email, phone, Aadhaar-style, PAN-style) and blocks rather than forwards it, since a question naming a specific identifier almost always means "look this up by X," which requires a blocked column to answer at all.
3. **SQL-level blocking** — after `sql_guard.validate_readonly_sql()` passes (guard only checks table names, not columns), a second check rejects the SQL if it references any blocked column by name, catching the case a table-level guard structurally cannot: `SELECT contact_email FROM dim_outlet` passes the guard (dim_outlet is approved) and is caught here instead.
4. **Result-level blocking** — a final check on the actual result rows' column names, independent of what the SQL text looked like, as a last line of defense.

Any hit at any layer returns `mode="blocked"` with a fixed, generic message ("Sorry, personal data cannot be queried through Ask Anything.") — never the original question, a detected value, or a stack trace. Blocked requests are logged with a safe reason token only (`ask_privacy_blocked reason=blocked_sql_column`, etc.) — never the question text or the value that triggered the block.

**This is defense-in-depth, not a claim of mathematical perfection.** The regexes are heuristic (a bare 10-digit number can false-positive as a phone number — an accepted over-blocking trade-off, not a bug); the SQL-level check is a word-boundary scan, not a real SQL parser. The application uses deterministic allowlisting and multiple validation layers to prevent protected personal-data fields from being exposed to the LLM or returned through Ask Anything — it does not claim this is impossible to defeat, only that it is checked at four independent points rather than one.

## Bugs found and fixed during verification

**`/service/fill-rate` 500 on `group_by=outlet` + fiscal period (Phase 4 pass).** The period-filter stitching used `period_sql.replace("AND ", "")`, which strips every "AND " in the string, not just the leading one, corrupting `BETWEEN ? AND ?` into `BETWEEN ? ?`. Not covered by the Phase 3 checkpoint's tests (only tested with `month`, never with fiscal-quarter params, on this endpoint). Found by a full endpoint sweep before shipping the frontend; fixed with `.removeprefix("AND ")`.

**Out-of-range `fiscal_quarter` caused a raw 500 instead of a clean validation error (Phase 5 pass).** `fiscal_quarter` was typed as an unconstrained `Optional[int]` on four endpoints (`/service/fill-rate`, `/service/otif`, `/money/freight-cost-per-case`, `/money/returns-leakage`, `/cold-chain/excursions`, `/cold-chain/returns`); a value outside 1-4 hit an unhandled `KeyError` inside `fiscal_quarter_bounds()` and returned a bare "Internal Server Error" with no JSON body. Found during the Phase 5 endpoint sweep. Fixed by constraining the query parameter to `ge=1, le=4` on all affected endpoints, so out-of-range input now returns a proper 422 with a field-level error message. Re-verified all 8 illustrative questions and the full endpoint/parameter matrix after both fixes.

**`ASSIGNMENT_PACK_DIR` unset resolved to a bogus absolute-path mount, exposed on the first real Docker Desktop test.** Everything before this point was verified statically (YAML parse, port/env/volume cross-checks, native uvicorn/vite runs) because the sandbox this project was built in has no Docker daemon. The first actual `docker compose up --build` run, on the user's own Docker Desktop, failed immediately with `the path /partner_api is not shared from the host and is not known to Docker`.

Root cause: `docker-compose.yml` originally mounted `${ASSIGNMENT_PACK_DIR}/partner_api`, `${ASSIGNMENT_PACK_DIR}/bazaarpulse_site`, and `${ASSIGNMENT_PACK_DIR}/data` as runtime bind mounts, with no `.env` present. Compose's default behaviour for an unset interpolation variable is to substitute an empty string and print a warning, not to fail — so `${ASSIGNMENT_PACK_DIR}/partner_api` silently became the literal, absolute path `/partner_api`. Docker Desktop's File Sharing has no way to have allow-listed that, because it isn't a real directory and never could be.

Fix, in two parts:
1. `docker-compose.yml` now uses Compose's required-variable syntax (`${ASSIGNMENT_PACK_DIR:?<message>}`) everywhere the variable is used, so an unset or blank `.env` fails `docker compose` immediately with a clear, specific error instead of silently degrading to a nonsense path.
2. `bazaarpulse_site/` and `partner_api/` — both small, static, synthetic fixtures supplied with the assignment pack (confirmed via the pack's own `README_START_HERE.md`: "All data is synthetic and generated for assessment purposes") — were moved from runtime bind mounts to **build-time** `COPY`, using Compose's `additional_contexts` (`docker/bazaarpulse.Dockerfile`, `docker/partner-api.Dockerfile`). Only `data/kestrel_ops.db` (95MB) and `data/csv/` (82MB) — genuinely too large to bake into an image, and read fresh by the ETL step each run — remain a runtime bind mount.

Why this is the actual fix and not a workaround for one machine: a `volumes:` bind mount to an arbitrary host path is a live share, gated by Docker Desktop's File Sharing allow-list on every platform that has one. A Docker build context is a one-time file read performed by the Docker CLI when you run `docker compose build`; it is not a live mount and is not subject to that allow-list at all. Moving the two small fixtures to build time removes the File-Sharing dependency for them entirely, on any OS, not just after manually adding a folder to Docker Desktop's settings. The one remaining bind mount (`data/`) still needs the assignment pack to be somewhere Docker Desktop shares — which on macOS is anywhere under `/Users` by default, covering the common case without extra configuration; this is now called out explicitly in the README's troubleshooting section for the uncommon case where it isn't.

**`fiscal_year` had the same unbounded-input bug as `fiscal_quarter`, found in the same audit pass.** `fiscal_quarter` was bounds-checked in the previous pass; `fiscal_year` wasn't. `fiscal_year=0`, negative, or absurdly large (e.g. `99999`) hit an unhandled `ValueError` from Python's `date()` constructor inside `fiscal_quarter_bounds()` and returned a bare 500. Fixed with `Query(ge=2000, le=2100)` on all six affected endpoints (the same set as the earlier `fiscal_quarter` fix, since they share `period_filter()`). Regression-tested in `backend/tests/test_validation.py` (parametrized across all six endpoints × several invalid values), which fail before ever touching the database — Pydantic validates query params before the handler runs — so this test file runs in any environment, including a clean checkout with no warehouse built yet.

**SQL guard: quoted-identifier bypass, closed before the LLM path that needs it went live.** `sql_guard.py`'s table allowlist only matched bareword identifiers after FROM/JOIN; `FROM "information_schema"."tables"` didn't match the regex at all, so the disallowed-table check saw nothing and the query passed untouched. Found in the audit, unreachable at the time (the LLM path this guards was `mode="llm_not_implemented"` and never ran generated SQL) but fixed proactively since it's exactly the control meant to protect that path once implemented — which it now does; every LLM-generated query goes through this same guard before execution. Rewrote the table-reference regex to handle bare, quoted, and schema-qualified identifiers in any combination, including comment-obfuscated separators (`FROM/**/foo` is valid SQL — a real SQL lexer treats a block comment as equivalent to whitespace, and a naive `\s+`-based separator regex misses that; found while writing the test for it, fixed in the same pass). Schema-qualified references are never exempted by a matching CTE alias name (CTEs can't be schema-prefixed in DuckDB), closing a second, related bypass where a CTE could be named the same as a disallowed table to smuggle a qualified reference past the allowlist. 21 new unit tests in `backend/tests/test_sql_guard.py`: allowed queries, bare/quoted/schema-qualified disallowed tables, JOIN-side disallowed tables, every forbidden mutation keyword, and SQL-injection-shaped input.

**SQL guard: comma-separated FROM bypass, found and closed in final release audit.** During final adversarial testing, a comma-separated FROM table-list bypass was discovered and closed; explicit JOIN syntax is now required for analytical queries.

**Near-expiry: `near_expiry_days` and `group_by` weren't validated like every other endpoint.** `near_expiry_days` had no bounds (a negative or absurd value wouldn't crash, just silently return a degenerate result); `group_by` was a bare `str` that silently fell back to `"category"` on bad input instead of rejecting it, unlike every other `group_by` param in the API (which are all Pydantic `Literal`s that 422 on an unknown value). Fixed: `near_expiry_days` is now `Query(30, ge=1, le=365)`; `group_by` is now `Literal["category", "warehouse"]`.

**BazaarPulse scraper: robots.txt claim didn't match the mechanism.** The scraper's docstring said "Respects robots.txt: skips /internal/ and /admin/, honours Crawl-delay: 1" — true in outcome (checked against the file), but there was no actual `robots.txt` fetch/parse anywhere; the behaviour was hardcoded from a one-time manual read. Given the brief explicitly frames "treat robots.txt as you would on a live site" as something being assessed, implemented it for real rather than just fixing the wording: `urllib.robotparser` (stdlib, no new dependency) fetches and parses `robots.txt` once per run, every request goes through `can_fetch()` first, and the crawl-delay is read from the policy instead of hardcoded (falling back to the documented default only if robots.txt itself can't be fetched). Re-ran the full 4-city scrape against the real mock site afterward: identical output to before (1,145 listings, 0 unparsed prices), confirming the change is purely additive.

## What we'd do next with two more weeks
Resolve the OTIF tolerance question with Kestrel's ops team directly rather than leaving it as a reported ambiguity; reconcile delay_minutes against its true source system; extend price matching with a proper string-similarity library if the 46% ambiguous rate matters to the business; give the LLM path a second model call to phrase the final answer from actual result rows instead of a pre-results `answer_intro`, if the current phrasing (written before the model sees data) ever reads oddly against real numbers.

## What breaks first in production
No auth or rate-limiting on the API. Single DuckDB file with no concurrent-write story — fine for a read-only analytics workload at this volume, not fine if this becomes a write path. At 100x data volume, the per-request DuckDB connection-open pattern and full-table scans in several endpoints (e.g. `fill_rate` over all order lines) would need indexing/pre-aggregation. All five Docker images run as root (no `USER` directive) — standard hardening gap, low blast radius here (no untrusted code execution, single-tenant), but a real one before this went anywhere multi-tenant. No structured server-side logging beyond uvicorn's default stderr — fine for a take-home, not fine for actually debugging a production incident; would want request logging with correlation IDs and the query text on 500s before this served real traffic. (Frontend dependency reproducibility, raised in the same audit: not actually a gap — `frontend/package-lock.json` is committed and the Dockerfile uses `npm ci`, which installs the exact locked versions regardless of the `^`-range in `package.json`.)
